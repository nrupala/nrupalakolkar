Fixing a Firefox-only SSL error by switching off Cloudflare ECH

The symptom

A Cloudflare-fronted site loaded in Chrome and failed in Firefox with SSL_ERROR_ECH_RETRY_WITHOUT_ECH. Same machine, same network. When one browser fails and another does not, the fault is usually in what the failing browser demands — not in the server.

What was happening

ECH — Encrypted Client Hello — hides the hostname inside the TLS handshake. Cloudflare publishes the ECH public keys in the domain's HTTPS DNS record, as an ech= parameter. Firefox reads that record and refuses the connection when the keys are inconsistent. Chrome tolerates the inconsistency.
Queried over DNS-over-HTTPS seconds apart, the HTTPS record returned two different ech= values. The edge was advertising inconsistent keys, and Firefox declined to proceed.

Diagnosis

Ask any DoH resolver for the HTTPS record and compare ech= across queries:
# repeat a few times, seconds apart curl -s "https://cloudflare-dns.com/dns-query?name=example.com&type=HTTPS" \ -H "accept: application/dns-json" | grep -o 'ech=[^ ]*' | cut -c1-40
A changing key prefix is the diagnosis. No ech= at all means ECH is not advertised — look elsewhere.

The fix

Cloudflare's free plan has no dashboard toggle for ECH. The API exposes it. The safe path:
  • Create a one-time token with the minimum scope: Zone → Zone Settings → Edit, limited to the single zone.
  • PATCH /zones/{zone_id}/settings/ech with {"value":"off"}, then read the setting back.
  • Repeat the DNS check until ech= is gone and stays gone.
  • Delete the token. It served its one purpose.
Nothing else on the zone changes — no TLS versions, no DNS records, no Universal SSL. The edge simply stops advertising ECH keys.

The pattern worth keeping

One-time, least-privilege API tokens: scope to the single job, use once, delete immediately. No standing credential, no standing risk.

Result

Firefox loads the site. The fix was one API call and a deleted token — the diagnosis was the work.
