The Error Message That Guessed

P.Eng. — 24+ years, safety-critical energy systems
2026-11-25 · Field Notes with Muse
My phone kept saying another app was using the microphone. No app was. The permission was off, and my own error message had been guessing instead of measuring.

The message on my phone was clear, confident, and wrong.
"Couldn’t open the mic — another app may be using it."
It appeared every time I tapped the microphone in a keyboard app I am building for my own phone. Not sometimes. Every time. And a message that fails every time, in exactly the same words, starts to feel like a fact.
It was not a fact. It was a guess my own software had been making, politely, in my own voice, for as long as that line of text had existed.

The test that broke the story

The first crack in the story was simple. In the very same place, at the very same moment, two other voice tools on the same phone worked perfectly. I could dictate into them without a murmur of complaint.
So the microphone was not broken. And no other app was holding it hostage — the other tools were using it freely, one after another.
That left an uncomfortable possibility. The problem was not the microphone, and it was not another app. The problem was inside my own app — and my own app had been pointing at the neighbours.
I should say what kind of app this is, because it explains why the fix was not obvious. It is a keyboard. When you type with it, it is the keyboard — not a normal app with its own screens and buttons. And a keyboard lives under a strange restriction: it cannot pop up the familiar request that asks you, "Allow this app to use your microphone?" That request belongs to regular apps. A keyboard has to be granted its permission somewhere else, in the phone’s settings, by hand.
Nobody had granted it. That was the whole story.

How the app got into that state

The build I was testing had arrived in an unusual way. It was a test build, made by an automated builder, signed with a throwaway key — the kind of key you use for a rehearsal, not for the real performance.
Because that key was different from the key on the version I normally use, the phone would not simply update the old app. The old one had to come off first, and the new one went on fresh.
A fresh install is a clean slate in ways you do not always remember. Settings start over. And permissions — the quiet yeses you granted months ago and forgot — start over too. The microphone permission I had granted long ago was gone, wiped with the old install, and the fresh app stood on my phone with its hand out and no way to ask.
So every tap on the microphone went like this. The app tried to start listening. The system refused, because the permission was off. The app reported the only sentence it had for that moment: another app may be using it.
I turned the permission on in Settings. The next tap, dictation started. The microphone had been free the entire time.

A sentence that covered three different failures

Here is the part that stayed with me, because it is the part that generalises.
When I traced where that message came from, I found it was not tied to one failure. It was the single sentence printed whenever starting the microphone failed — and starting could fail at three different points, for three different reasons. A part might fail to initialise. The recorder might be in the wrong state. The recording itself might refuse to begin.
Three different problems. One sentence. And the sentence did not describe any of them. It described a fourth thing — a guess about what might be happening outside the app, offered because it sounded plausible.
Think about what that does to the person reading it. I spent my first minutes investigating the wrong world: other apps, other tools, the microphone itself. The message sent me there. A wrong diagnosis is not neutral. It is a set of directions to the wrong address, delivered with confidence.
And notice the quiet trap inside it. If a real case of "another app is using it" ever did happen, this message would look correct — by luck. A guess that is sometimes right by accident is harder to catch than one that is always wrong. Mine was caught only because it failed every single time, in a place where other tools worked. A subtler version of the same guess could have lived in that app for years.

What the fix looks like

The fix is not a better guess. It is a refusal to guess.
First, check the permission before trying to listen. That is a fact the app can know in one step, with no interpretation. If the permission is off, the message should say exactly that, and say where to turn it on: "Microphone permission is off — open Settings to allow it." Measured, specific, and finished.
Second, when starting fails anyway, record which of the failure points actually fired, and what the recorder’s state was at that moment. Not for the user — for the record, so the next investigation starts from evidence instead of from a sentence someone wrote on a hopeful afternoon.
Third, the old clause only earns its place back if it can be proven at the moment it is printed — if the system itself shows another recording genuinely active. A cause you have not measured does not go in the message. It goes nowhere.
There is a small tool beside this post that checks the pattern in any codebase: one catch-all message stretched across several different failure points is flagged, because a message like that cannot be telling the truth about all of them.

The lesson

We tend to treat error messages as decoration — the words you write last, quickly, for a case you hope never happens. Then the case happens, and those words are the only witness the user gets.
A witness should report what it saw. Mine reported what it imagined.
So the rule I now hold my own work to is a plain one. An error message may say what was checked and what was found. It may say what to do next. It may not invent a cause it never measured — however reasonable the invention sounds, and however many times it has got away with it.
The microphone was never busy. The permission was off. The distance between those two sentences was one honest check — and a message that should never have been allowed to guess.
