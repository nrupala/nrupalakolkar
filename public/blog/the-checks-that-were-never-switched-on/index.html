The Checks That Were Never Switched On

P.Eng. — 24+ years, safety-critical energy systems
2026-11-26 · Industrial Intelligence
Every test passed — 344 of them. Then a new part of the system switched the written promises on for the first time, and two of them turned out to be broken.

Every test passed. Three hundred and forty-four of them.
I was building a calculation engine — the kind of software that works out the numbers engineers rely on when they size and protect electrical equipment. Each function in it carries a small written promise beside it. This input will stay inside these limits. This result will keep this exact relationship to that one. Promises like that are called contracts, and they are the reason you can trust a calculation you did not do by hand.
That morning, the whole battery was green. And a new piece of the system, built separately, did something none of my tests had ever done.
It switched the contracts on.

The green that proved less than I thought

Here is the quiet fact I had missed for weeks.
A contract in code does not enforce itself. When the program is built, a setting decides whether those promises are checked while the program runs, or whether they are simply written down and ignored. My test programs had been built without that setting. Every one of them.
So my tests had been answering a narrower question than I believed. They checked that the answers matched the expected numbers — and they did, every time. But they never checked that the promises held along the way, because the part of the machine that watches the promises was never switched on.
The numbers were right. The proof that the numbers were produced inside their promised limits did not exist. I had been reading the first as if it were the second.
Nothing had failed. That was the problem. A check that is switched off does not fail loudly. It fails by staying silent, and silence looks exactly like success.

Two violations, hiding in eight batteries

We rebuilt all eight test batteries with the contracts switched on and ran them again, one by one.
Six batteries passed completely, start to finish. Then the seventh stopped dead.
A promise had been broken — not in a dark corner, but on a standard textbook example, the kind of worked problem students learn from. And when we fixed that one and ran again, the battery stopped a second time, further in. A second broken promise had been hiding behind the first, the way one fallen tree hides the next one on a trail.
Two violations. That was all, across three hundred and forty-four checks. But each one taught a different lesson, because in one case the promise was wrong, and in the other case the code was.

When the promise is the mistake

The first function takes a value measured at one voltage level and restates it at another. Its promise said the two levels could differ by no more than ten to one — in either direction. Neat. Symmetric. Tidy.
The textbook example that broke it steps down by almost twenty-one to one. An ordinary, everyday step-down of exactly the kind the function exists to serve.
So we asked the question that matters before touching anything: what was the ten-to-one limit actually protecting?
The answer was clear once we did the arithmetic. In the upward direction, the limit is load-bearing. The result grows with the square of the ratio, and the cap is exactly what keeps the result inside its promised bound. In the downward direction, the limit protected nothing at all. A smaller ratio only makes the result smaller. There was no overflow to fear, no bound to break. The floor was there because symmetry looked right when someone wrote it — not because the numbers needed it.
We removed the downward floor and kept the upward cap, and we wrote the reason beside the promise, so that no later reader tidies it back into symmetry and reintroduces the failure as a cleanup.
A promise can be wrong. When it is, fixing the code to obey it would have been the real mistake.

When the code is the mistake

The second function builds a pair of values that must keep an exact relationship: the second is the first, multiplied by a stated factor. Its promise says so, in those terms.
The code scaled both values separately, from a common starting pair that already kept the relationship exactly. In ordinary arithmetic, that is safe. In the arithmetic a computer actually does — where every result is rounded to the nearest value the machine can hold — it is not. Multiply in one order and you land on one value. Multiply in the other order and you land one step away. The smallest step the format can represent. One step, and the promise was false.
For a long time, a separate automated proof tool had refused to certify this function. We had carried that refusal as an open item — a proof we could not yet complete. The switched-on contract showed us the truth in plain terms: the proof tool was not failing. It was right. As written, against that code, the promise simply was not true.
So this time we left the promise untouched and fixed the code. The second value is now built from the first, after scaling — so the relationship holds by construction, exactly, every time. The answer moved by that one smallest step, far inside the tolerance the textbook example allows. And the proof tool, given the corrected code, certified the function on its next run.

The standing rule now

The fix that matters most is not either of those two. It is the third change, the boring one.
The contracts are now switched on in the standing build — not only in the test programs, but in the shared core itself, because a check that lives only in the tests can be quietly lost the day someone links the core into something new. What is checked must be checked everywhere the code runs, or the green is a local opinion.
And the full battery, run that way, passes entire: three hundred and forty-four out of three hundred and forty-four, with the promises enforced this time, not just written.

The lesson

Every builder has a version of this story. A warning light that was never wired. A guard that exists on paper and was never connected to the machine. Tests that pass, beautifully, while quietly answering a smaller question than the one you asked.
So the habit I take from that morning is a plain one. When a result is green, ask what was actually switched on to produce the green. Ask which checks ran, and which were only present — written, visible, reassuring, and inert.
A promise in the code is a good thing. A promise the build enforces is a better one. The distance between those two is one setting — and, in my case, two honest failures that had been waiting patiently for someone to turn the light on.
