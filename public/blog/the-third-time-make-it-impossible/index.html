The Third Time, Make It Impossible

P.Eng. — 24+ years, safety-critical energy systems
2026-11-17 · Trust Rails
The same silence came back on three different sites. The first two times I fixed the page. The third time I fixed the reader itself — so the bug has nowhere left to live.

I pressed play, and the voice read the title — and then stopped.
The words were right there on the screen. Paragraph after paragraph, all the way down the page. My eyes could see them. The reader could not. It had arrived, looked around, found a headline and a short opening line, and decided that was the whole article.
It was not a new bug. That was the worst part. It was an old bug, wearing a new address.

The first time, I fixed the page

The first time it happened, the cause seemed simple once we found it.
A web page is built in order, from the top down. The browser reads it the way you read a letter — line by line, in sequence. My read-aloud tool was placed partway down the page, and it did what it was told the moment it appeared: it woke up, collected everything it could see, and got ready to speak.
But at that moment, the rest of the page did not exist yet. The browser had not reached it. So the tool collected the headline, the opening line, and nothing else — not because the words were hidden, but because they had not arrived.
We fixed that page. We moved things around until the tool woke up after the words were there. Play worked. The whole article was read, start to finish. Fixed, we said. And it was — on that page.

The second time, I fixed the page again

Then it happened on a different site.
Different design. Different page. Same silence after the headline.
We knew the cause this time, so the fix was faster. Once again we adjusted that page — its layout, its order — until the reader could see the full text before it started. Once again, play worked. Once again, we called it fixed.
I want to be honest about what we had actually done. We had not fixed the tool. We had fixed two pages, one at a time, by hand. The tool itself had learned nothing. Put it on a third page in the wrong order, and it would fail in exactly the same way, for exactly the same reason.
That is not a solution. That is a habit of rescue.

The third time, he asked the right question

The third time, the same failure showed up on article pages built a third way. Headline read aloud. Body silent. The pattern was no longer a coincidence. It was a family.
And this time, the question came from the person who owns the work, and it was not about the page at all. It was, in substance: this has happened three times now. Where is the learning? Where is the memory? Why does the same bug get to keep coming back?
He was right, and the honest answer stung. The learning existed — as notes. Each failure had been written down. Each fix had been recorded. But a note is a thing a person has to remember to read at the right moment, on the right day, while doing a different job. Notes wait politely. Bugs do not.
We had been storing the lesson in the one place it could not protect us: in our memory of the last rescue, instead of in the tool itself.

Fix the physics, not the page

So the third fix went in a different place. Not in any page. In the reader itself.
The rule is one line long, and it is now part of how the tool starts, every time, on every page: if the page is still being built, do not start. Wait until the page says it is complete. Then collect the words.
That is all. If the document is still loading, the reader waits for the signal that loading has finished. If the page is already complete, the reader starts at once. Where the tool is placed on the page — above the article, below it, in the middle — no longer matters. The order cannot hurt it anymore, because the tool refuses to judge a page that is not finished yet.
We did not move a single page this time. We changed what the tool is allowed to assume. A half-built page is not a small page. It is an unfinished one, and the correct response to an unfinished page is patience, built into the code.

A test that remembers for us

A rule in code can still be removed by a careless edit next year. So the fix came with a guard that does not forget: a test that rebuilds the original trap on purpose.
The test places the tool early, lets the page finish building after it, and then checks that the late words are still collected and read. Run against the old version of the tool, that test failed four times — the old code wrapped only the headline, exactly as it had in real life. Run against the fixed version, it passed every check: twenty-four out of twenty-four.
Afterwards we checked the real pages, not just the test. On the live articles that had failed, the reader now wrapped the whole body — dozens of sentences where before there had been two. The silence was gone, and this time it was gone for a reason that lives inside the tool, not inside our recollection of the last time it broke.

The rule I keep now

Here is the rule that came out of that third failure, and I now apply it far beyond one reader.
When a failure appears once, fix the instance. That is honest work. When it appears a second time, you are no longer looking at an accident. You are looking at a pattern asking a question: what in the design allows me to exist?
And if it appears a third time, the answer is no longer another careful fix. The third time, make it impossible. Change the shape of the thing so the failure has nowhere left to live. Then write the test that proves the old shape fails and the new shape holds — because a lesson that lives only in notes will be relearned at full price.
Most teams do not lack lessons. Their post-mortems are full of them. What they lack is lessons that have been promoted — from a paragraph someone once wrote, into a property the system itself enforces on its worst day, when nobody remembers.

A check you can run today

You do not need my reader to steal the useful half of this. Any tool that starts itself inside a page someone else builds can be checked the same way: does it wait for the page to finish, or does it trust the order it was placed in?
Ask of any tool that starts on a page:
1. Can it start before the page has finished building?
2. If it starts early, what does it miss — and would anyone notice the missing part?
3. Is the wait written into the tool itself, or does every page have to remember to be kind?
4. Is there a test that rebuilds the early start on purpose — and fails on the old code?
If the answer to 1 is yes and the answer to 4 is no, the bug is not fixed. It is just between visits.
The small script shipped with this post does the mechanical half for my kind of tool: it reads a script file and checks whether the start is guarded — whether the code waits for the page to finish when the page is still loading. It cannot judge whether your tool is good. It can tell you whether your tool is patient, which is the half that failed in my story.

The silence I do not expect to hear again

I still press play on new pages with a little care. But the care is different now. I am no longer checking whether we remembered the lesson on this particular page. I am listening to a tool that carries the lesson inside itself, on every page, whether anyone remembers or not.
That is the whole difference between fixing a bug and finishing with it. A fix is something you did. Impossible is something you built.
