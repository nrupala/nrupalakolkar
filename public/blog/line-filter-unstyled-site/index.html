The line filter that unstyled my whole site

P.Eng. — 24+ years, safety-critical energy systems
2026-10-17 · Field Notes with Muse
The site was up, and the site was broken. Both stayed true for two days, because up was the only claim my monitoring tested.

What happened

On October 15, I removed Google Fonts from this site. The change was deliberate: I do not want third-party dependencies woven into my own surfaces, so the fonts came out and the pages were switched to native system font stacks. The commit was small and, by every check I ran at the time, clean.
The removal was executed as a line filter. Every line that mentioned the fonts domains was deleted.
That is where it went wrong. These pages are compact HTML. On many of them, the inline <style> block shares a single line with the font @import statement. Deleting the line did not delete the font reference. It deleted whatever else happened to be on that line.
Across 18 pages, the damage came in three shapes. On 12 pages, the filter removed the opening <style> tag plus the first chunk of CSS. On 4 pages, it removed the entire style element. On two pages — the card page and the consulting page — it removed a whole mega-line that carried meta tags, the style block, and the start of the body.
The result was a site that rendered completely unstyled: raw CSS text dumped at the top of the page, no layout, and accordion sections that could not open visually because the styles that drive them were gone. The scripts were still there. The content was still there. The page just had no clothes.
It stayed that way for two days. I found it myself, by visiting my own site.

Why nothing caught it

Every automated check I had passed. The server returned HTTP 200 with correct headers. Deployment-state monitoring was green. The host-inventory check — which third-party hosts a page loads — was green, and in a narrow sense it was right: the fonts really were gone.
But none of those checks look at the thing that actually broke. A 200 status code tells you a file was served. It tells you nothing about whether the file is whole. My monitoring watched the deployment and the edges of the page. Nothing watched the rendered structure in the middle: whether the stylesheet exists, whether the document is the size and shape it is supposed to be.
This is the part I keep relearning in different forms: a green checkmark is only as good as the invariant it actually tests. "The site is up" and "the site is intact" are different claims, and I was only testing the first one.

The diagnosis

The diagnosis was byte-level, because at that point I did not trust anything else. The live homepage contained zero opening <style> tags and one closing tag. That single count localized the failure: the stylesheet had not failed to load; its opening tag had never been served.
Git archaeology found the commit and its parent. One caution from that process: the local clone I had on hand was stale — it predated the breakage entirely, and diffing against it would have told me a reassuring story that was false. GitHub's main branch was the source of truth, and it matched the broken live bytes exactly. The site had been broken since the evening of October 15, not since anything I did that day.

The repair

The repair discipline mattered more than the repair itself. A broken stylesheet tempts you to rewrite it. I did the opposite: each of the 18 pages was restored to its exact pre-commit bytes, minus only the @import statement — the one change that had actually been intended. Every restored style block was mechanically proven byte-equal to the parent version minus the import before anything shipped.
Two points in that. First, restoring to a proven state beats patching forward from a damaged one; you end up knowing exactly what you have. Second, the intended change survived the repair. The bug was in the method of the fonts removal, not in the decision. The fonts stay removed.
The fix went out as a single commit. The deploy pipeline ran, and I verified the result two ways: the live bytes (style tags balanced, sizes restored) and a fresh-browser render, because after this incident I was not going to call bytes alone a verification.

The invariant, encoded

A lesson written down is a lesson I will have to learn again. So the same night, the check that would have caught this became code: a small probe that fetches six key pages and asserts the structural facts — style tags present and balanced, no Google Fonts hosts anywhere in the bytes, and served size above a floor that catches truncation. It runs daily, inside the site-integrity check that already existed. It does not replace the deployment monitoring; it tests the claim that monitoring was always supposed to cover.
Here it is, cleaned up. Thirty-odd lines, no dependencies beyond curl:
Download style_check.py — or copy it below.
#!/usr/bin/env python3 # style_check.py # Structural probe for key pages: asserts the stylesheet is present and # balanced, no third-party font hosts appear in the bytes, and the served # size is above a floor that catches truncation. A page can serve # HTTP 200 and still be unstyled -- this catches that. # From: https://nrupalakolkar.com/blog/line-filter-unstyled-site # Usage: python3 style_check.py """Assert that key pages are structurally whole, not just served.""" import subprocess, sys PAGES = [ ("https://example.com/", 20000), ("https://example.com/blog/", 8000), ("https://example.com/card/", 3000), ("https://example.com/consulting", 8000), ] def fetch(url): out = subprocess.run( ["curl", "-sS", "--max-time", "30", "-w", "\n%{http_code}", url], capture_output=True, text=True) body, _, code = out.stdout.rpartition("\n") return int(code), body findings = [] for url, floor in PAGES: code, body = fetch(url) if code != 200: findings.append(f"{url}: HTTP {code}") continue opens, closes = body.count("<style"), body.count("</style>") if opens < 1 or opens != closes: findings.append(f"{url}: style tags unbalanced " f"(opens={opens}, closes={closes})") if "fonts.googleapis" in body or "fonts.gstatic" in body: findings.append(f"{url}: third-party font host present") if len(body) < floor: findings.append(f"{url}: {len(body)}B, below floor {floor}B") for f in findings: print(" -", f) sys.exit(1 if findings else 0)
None of these checks is clever. That is the point. The failure was not subtle, and it survived for two days anyway — not because it was hard to detect, but because nothing was assigned to detect it. If a property of your system matters, there should be a small, boring program whose only job is to keep saying so.
