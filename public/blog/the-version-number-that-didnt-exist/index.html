The Version Number That Didn't Exist

Everything on my own machine said the work was fine.
The tests passed. The build passed. The new version — a small step up, the kind of change you make without thinking twice — sat there looking ready. Then the work went out to a clean machine, one that had never seen it before, and that machine refused it outright.
Not because the code was wrong. Because one line in a list claimed that a piece of software, written by strangers, existed at a version it has never existed at. We had invented a release. Quietly. With one careless command.

The smallest edit in the building

Here is how a version bump usually goes.
A project is not one piece of software. It is a family: several parts that we build ourselves, living in one workspace, sharing one version number. Around them sits a much longer list — the lockfile — naming every outside package the project depends on, and the exact version of each one. The lockfile is a promise. It says: build this project anywhere, and you will get these exact pieces, in these exact versions, every time.
Our parts needed to move from 0.6.2 to 0.6.3. A small step. The kind of edit that feels too small to review.
So the bump was done the fast way: find every "0.6.2" in the lockfile, and replace it with "0.6.3". One command. Done in a second. The file still looked tidy. Our own parts now carried the new number, exactly as intended.
What the command could not see — what a blind replace never sees — is that the same three digits can belong to more than one owner.
Three outside packages, written by other people, also happened to sit at version 0.6.2 that day. The replace rewrote them too. All three were now listed at 0.6.3 — a version that, for at least one of them, has never been released. It does not exist. It never did.
Nobody typed a lie. A search-and-replace does not know what a lie is. It just found the pattern it was told to find, everywhere it was told to find it.

Why my machine believed it

If the lockfile pointed at a version that does not exist, why did everything pass at home?
Because my machine was warm.
A working computer keeps copies of things it has already fetched. When the build ran locally, it reached into that warm store, found the real packages it already held, and carried on — never forced to go and fetch the invented version from the outside world. The corruption was in the list, but nothing at home ever had to prove the list true.
The clean machine had no such kindness to offer. It started cold, with an empty store. It read the lockfile the way a stranger reads it: as the whole truth. It went looking for the version we had named, in the place such versions live, and found nothing — because there was nothing to find. The build failed at the very first step, before a single line of our code was even judged.
That is the part of this story I keep coming back to. The failure did not happen on the cold machine. The failure happened at my desk, with the replace. The cold machine was simply the first place honest enough to say so.
A green build at home had been telling me something much weaker than I thought. It had been telling me: this works on a machine that already believes it.

The repair, and what it cost

The fix was not clever. It was careful, which is a different thing.
We went back to the last lockfile that the clean machine had accepted — the last list known to be true — and started again from there. This time, the version was changed only inside the blocks that belong to our own parts, and in the places where those parts name each other. Every outside package kept its real version, untouched, down to the last digit.
Then came the part that matters most: we verified it cold.
A fresh, empty build space. No warm store to lean on. The project was made to prove, from nothing, that every version in its list could actually be fetched and that the whole thing held together. Only when it passed that way — the stranger’s way — did we call it fixed.
It took far longer than the one-second replace that caused it. That is usually the exchange rate. Carelessness is fast and bills you later, with interest. Care is slow once, and then it is done.

The rule that came out of it

The rule in my house now fits in one breath: never blind-replace a version. Ever.
A version number is not a piece of text. It is a name, and names have owners. When the same digits appear in ten places, they may belong to ten different owners, and changing all of them because they look alike is like renaming every person in a room because they happen to be wearing the same colour.
So the method is fixed. Start from the last list that was proven true. Change only what is yours. Leave every stranger’s name exactly as they wrote it. And then — this is the half people skip — prove it cold, on an empty machine or in an empty space, where nothing is cached and nothing is forgiven.

A check you can run today

You do not need my exact tools to steal the useful half of this. Any project with a lockfile — a list of the exact versions it depends on — can be checked the same way after a version bump: compare the list before and after, name every package whose version changed, and ask one question of each — is that package ours?
After any version bump, ask:
1. Which packages changed version between the old list and the new?
2. Is every changed package one of OUR OWN parts?
3. Did any outside package move? If yes — stop. That change was not yours to make, and the new version may not even exist.
4. Does the project still build from an empty, cold space — not just on the warm machine where the edit was made?
If question 3 has any answer at all, the bump is not done. It is damaged.
The small script shipped with this post does the mechanical half: it reads a lockfile from before a bump and one from after, lists every package whose version changed, and fails if a changed package is not on your own list of parts. It cannot judge whether your new version is wise. It can make sure you only renamed what was yours to rename — which is the half that failed in my story.

Small edits deserve real respect

I have come to think the most dangerous edits in any project are not the large ones. Large edits get plans, reviews, and second pairs of eyes. They arrive with ceremony, and ceremony is a kind of safety.
The dangerous edits are the ones too small to review. One command. Three digits. A second of work, done between two bigger thoughts, by someone — in this case, my own assistant, at my own direction — who had no reason to suspect that a tidy-looking pattern could belong to strangers.
A warm machine will cover for an edit like that. It covered for ours, politely, right up until a cold machine told the truth.
So now we ask the cold machine first. It is a less friendly witness. It is also the only one whose "yes" means the work will survive meeting the rest of the world — which is, in the end, the only yes that counts.
